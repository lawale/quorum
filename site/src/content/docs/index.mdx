## The approval flow every team rebuilds

<p class="lead">
Wire transfers, production access, price changes, content going live. The four-eyes principle shows up everywhere, and every team writes it again: a status column, a couple of endpoints, an audit table that is never quite complete, a UI only one app can use. Then the next app needs the same thing.
</p>

<div class="q-compare">
  <div>
    <h3>Rolling your own</h3>
    <ul>
      <li>Approval state lives in a column on your own table, with transitions scattered across handlers.</li>
      <li>Guards like "not the maker", "one vote per stage", "only managers" are re-implemented, and re-forgotten, per app.</li>
      <li>Changing who approves what means a code change and a deploy.</li>
      <li>The audit trail is whatever logging you remembered to add.</li>
      <li>Each app builds its own approval screens.</li>
    </ul>
  </div>
  <div class="q-with">
    <h3>With Quorum</h3>
    <ul>
      <li>Requests, stages, votes and expiry are a first-class model with enforced transitions.</li>
      <li>Layered guards are enforced centrally and configured per policy.</li>
      <li>Policies are data. Edit them at runtime in the console or the API.</li>
      <li>Every action is recorded with actor, timestamp and details, through a transactional outbox so nothing is lost.</li>
      <li>Drop in three themeable Web Components, or use the admin console.</li>
    </ul>
  </div>
</div>

<div class="q-section">
## How it works

<ol class="q-flow">
  <li><strong>Your app creates a request</strong><p>One API call with a type and a JSON payload. The caller is the maker.</p></li>
  <li><strong>Quorum matches a policy</strong><p>Rules live in data: stages, required approvals, who may act, when to expire.</p></li>
  <li><strong>Checkers decide</strong><p>Self-approval, roles, permissions, scope and duplicate votes are all enforced before a vote lands.</p></li>
  <li><strong>Your app acts on the result</strong><p>Approved, rejected or expired arrives by webhook, event stream or poll. Quorum decides, your app performs the write.</p></li>
</ol>
</div>

<div class="q-section">
## Built for production from day one

<CardGrid>
  <Card title="Layered permission guards" icon="seti:lock">
    Self-approval prevention, per-request eligible reviewers, per-stage roles and permissions, reviewer scoping, an optional dynamic authorization URL, and duplicate-vote prevention. Evaluated in order on every decision.
  </Card>
  <Card title="Audit-ready by default" icon="document">
    Every create, approve, reject, cancel, bypass and expiry is permanently logged with actor, timestamp and details. One place to answer "who approved this, and when" for SOC 2 or ISO 27001.
  </Card>
  <Card title="Webhooks that cannot be lost" icon="rocket">
    Deliveries are written to a transactional outbox in the same transaction as the state change, signed with HMAC-SHA256 and retried with backoff. A review_requested event tells your app exactly who may act next.
  </Card>
  <Card title="Embeddable widgets" icon="puzzle">
    Three Lit Web Components, an approval panel, a request list and a stage progress bar, with Shadow DOM isolation, CSS custom property theming and live updates over Server-Sent Events. Script tag or npm.
  </Card>
  <Card title="Your identity provider stays in charge" icon="approve-check">
    Validate JWTs against any OIDC provider's JWKS endpoint with claim mapping and automatic key rotation, or trust headers from your gateway. Quorum never becomes a user directory.
  </Card>
  <Card title="PostgreSQL or SQL Server" icon="seti:db">
    Everything lives in its own schema, so Quorum can share a database with your application. Prometheus metrics, a health endpoint and multi-arch Docker images are included.
  </Card>
</CardGrid>
</div>
